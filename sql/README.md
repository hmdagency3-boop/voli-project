# voli — External project setup

1. Connect your external project in Lovable: **Settings → General → External Supabase → Connect**. The integration generates the client and authentication configuration; no private key should be pasted into frontend code.
2. Run `voli-starter.sql` in the project's SQL Editor. It is safe to run again: it keeps existing rows, adds missing columns (such as `bio` and `updated_at`), refreshes grants, policies and the `public.handle_new_user` signup trigger, moves an older `private.account_uids` table to `public`, and creates the internal UID and profile for any user who signed up before it ran.
3. Enable Email in Authentication → Providers. Keep email confirmation enabled. Add the preview and published origins to Authentication → URL Configuration. Add `/reset-password` when recovery is connected.
4. After connection, wire the prepared login/signup form to the generated client, sending `display_name` in signup metadata. Successful signup with a null session requires email confirmation, not an immediate redirect as a signed-in user.

## Tables
- `profiles`: Auth UUID ownership, visible seven-digit random ID, display name, optional avatar and bio (up to 300 characters), `updated_at` refreshed on every edit.
- `public.account_uids`: hidden sequential internal UID, starting at 20000 (older numbers below 20000 are renumbered to 20000 and up, in their original order). Row level security is on with no policies and all app-role grants are revoked, so the Data API can never read or change it; never add a policy, grant or client-facing function for it. Sequence values may have gaps after rolled-back transactions and are not a total account count.
- `follows`: follow relationships.
- `streams`: live-stream metadata, not video delivery.
- `messages`: private direct messages; only sender and recipient can read them.

No fake accounts or seed data are included. Public IDs have nine million possible values, are unique, and retry on collision. They are identifiers, not secrets or authorization credentials. Internal numeric UIDs are never included in public profile rows. All user-owned writes are protected by RLS and column grants. Wallets, payments, VIP, gifts, video transport and realtime chat delivery are outside this starter setup.

## Updates (run after the starter file, in order; each is safe to run again)
- `supabase/001_levels.sql`: charisma and wealth points and the 100-level tables.
- `supabase/002_special_id.sql`: `vip_level` and `special_id` (الايدي المميز) on `profiles`. Only the admin sets the special ID from the SQL Editor, e.g. `update public.profiles set special_id = '777' where public_id = 1234567;`. A special ID is digits only, unique, and can never equal another member's normal ID. The app shows it instead of the normal ID, on a card chosen by VIP tier.
- `supabase/004_rooms.sql`: party rooms — one room per member (name, cover, audio/video, 5/10/15/20 mics, theme, announcement, optional 4–8 digit password), who is inside, mic seats, room chat, removing a member for 10 minutes, and a `room-covers` picture bucket. Live voice/video is not included.
- `supabase/005_room_coins.sql`: coins thrown inside a room. A member inside the room throws coins out of their own `profiles.coins` balance (`select public.throw_room_coins(room, amount)`), and the room header shows the room total (`select public.room_coins_total(room)`). The `room_coins` table itself stays closed to the app: no policies, no grants. Biggest single throw: `select public.room_coins_max_throw()` (1,000,000).
- `supabase/006_room_gifts.sql`: the gift box inside a room. The gift list and prices live in `room_gift_catalog` (members read it; change a price with `update public.room_gift_catalog set price = 50 where key = 'rose';`). A member picks people inside the room and sends `select public.send_room_gift(room, 'rose', count, array[...])`: the cost is price × count × people out of their own coins, the sender gains wealth points and each receiver gains charisma points. Gifts are written to `room_coins` with the receiver, so they count in the room total; `select * from public.room_gifts_received(room)` gives what each person received.
- `supabase/007_room_ranking.sql`: the room ranking (ترتيب الدعم والمدعومين). `select * from public.room_ranking(room, 'support' | 'received', 'day' | 'week' | 'month')` returns the top 50: `support` = coins thrown plus gifts sent, `received` = gift value received. Days, weeks (from Monday) and months follow Cairo time. Only people inside the room see it.
- `supabase/008_agencies.sql`: agencies (نظام الوكالات). A member applies in the app; management approves in the app (admin role) or with `select public.admin_review_agency_application('<id>', true);` and the agency gets the next code from 200. Hosts search the code and send a join request; the agent accepts or rejects and can remove hosts. Income counts only gifts received while a host is active in the agency. Set the agency share with `update public.agencies set commission_percent = 10 where code = 200;` (empty until the app policy decides it).
- `supabase/009_admin.sql`: the management panel at `/admin` (no link to it inside the app). Make yourself top management first with `select public.admin_set_role(<your public ID>, 'admin');`, then open `/admin` while signed in. The panel shows platform numbers, finds members (public ID, special ID, name or email), adds or removes coins, gives or ends VIP, sets the special ID, gives moderator/admin roles, fixes names and pictures, bans (days or forever; blocks new sign-ins, takes them out of every room and closes their live room) and unbans, closes rooms and clears room chat, edits gift and VIP prices, reviews agency requests, renames agencies, sets their share and removes hosts. Every action is checked against the admin role in the database and written to `admin_actions` (closed to the app), shown in the panel's log.
- `supabase/003_vip.sql`: the 8 VIP dragon tiers (`vip_tiers`, one column per feature), VIP grants from purchase / admin / gift / event with optional end date (`vip_grants`), coin balance, `buy_vip` purchase, admin commands (grant, revoke, add coins, set moderator/admin role), member settings (hide location from VIP 2, invisible mode from VIP 5), room rules ready for when rooms exist (`can_mute_or_kick`, `vip_room_entry`) and the monthly salary (`pay_vip_salaries`). Old 0–100 VIP values are moved to the tiers once (1–12 → 1 … 88–100 → 8). The admin commands are listed at the top of the file. Prices, durations, salary amounts and friends-list sizes are empty until you set them; nothing is for sale before that. To drop expired VIP from profiles, run `select public.refresh_all_vips();` (daily, e.g. with pg_cron).
- `sql/014_admin_grant_notices.sql` (after `supabase/010_admin_notices.sql` and the later updates): when management gives a member VIP or adds coins from the panel, the member gets an official English message from Voli Helper (ID 100), e.g. `Congratulations on your upgrade to VIP5, valid for 15 days.` Removing coins sends nothing; if Voli Helper does not exist yet the panel action still works without a message.

If you re-run `voli-starter.sql`, run the update files again afterwards so their grants come back.
